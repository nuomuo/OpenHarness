# Agent Harness 研发岗：能力模型与 20 周学习计划

> 目标：从"会用 AI 工具的人"变成"能造和改进 Agent Harness 的人"。
> 版本：2026-10。领域变化极快，每 4 周请对照最新模型/框架文档校订一次。

---

## 0. 先看清岗位：你要投的是哪一类

"Agent Harness 研发"不是单一岗位，招聘市场上至少分三条线。**先选线，再定学习重点**，否则什么都学一半。

| 线                                                       | 典型职位名                                                       | 核心工作                                                               | 硬门槛                                                 | 面试重心                      |
| -------------------------------------------------------- | ---------------------------------------------------------------- | ---------------------------------------------------------------------- | ------------------------------------------------------ | ----------------------------- |
| **A. Harness / Agent 平台工程师**（工程向）        | Agent Harness Engineer、Agent Runtime Engineer、Agent 平台工程师 | 运行时循环、工具层、权限沙箱、MCP 集成、多 Agent 编排、可观测性        | 强系统工程：并发、进程、文件系统、容器、Rust/TS/Python | 系统设计 + 编码 + 排障        |
| **B. Agentic Post-training / RL 工程师**（模型向） | Agent 算法工程师、Agent RL 工程师、后训练工程师                  | 可验证环境构建、rollout 基础设施、奖励设计、轨迹重建、小模型工具后训练 | 分布式训练、RL 基础（PPO/GRPO）、环境工程、Python/容器 | RL 原理 + 环境设计 + 实验设计 |
| **C. Agent 应用 / 解决方案工程师**（产品向）       | Applied AI Engineer、Agent 应用工程师                            | 用现成 Harness 交付业务价值、评测与调优、性能与成本                    | 快速交付、eval 方法论、领域理解                        | 项目深挖 + 评测设计           |

现实中的招聘信号（可直接搜来看 JD 措辞）：

- 苹果有明确以 *Applied AI Engineer, Agent Harness* 命名的岗位：[https://jobs.apple.com/zh-cn/details/200688056-0836/applied-ai-engineer-agent-harness](https://jobs.apple.com/zh-cn/details/200688056-0836/applied-ai-engineer-agent-harness)
- 国内大厂在"大模型算法工程师 - Agent 应用与强化学习方向"这类 JD 里，已把 *环境构建 + rollout + 评测* 写成硬要求。
- 这个岗位名是 2025–2026 才稳定的，**不要指望有成体系的课程或考证**。最好的教材就是：**源码 + 论文 + 你自己的实验数据**。

**建议**：如果你有后端/系统背景 → 主攻 A，用 C 做副线；如果你是算法背景 → 主攻 B；在校生 → A 最容易做出可见作品。

## 1. 能力模型：六个维度，按权重排序

| # | 维度                         | 权重                               | 你要达到的程度                                                                  |
| - | ---------------------------- | ---------------------------------- | ------------------------------------------------------------------------------- |
| 1 | **系统工程功底**       | ★★★★★                         | 能设计并实现一个多进程/多线程的可靠系统；理解沙箱、权限、信号、崩溃恢复         |
| 2 | **上下文工程**         | ★★★★★                         | 能讲清"每一轮模型看到什么、为什么、代价是什么"；能设计压缩与记忆策略            |
| 3 | **工具层设计**         | ★★★★★                         | 能设计出模型不容易误用的工具；知道错误信息也是 prompt                           |
| 4 | **模型理解（非训练）** | ★★★★                           | 懂 tokenization/chat template/采样/思维链/上下文成本/注入风险；不要求会训大模型 |
| 5 | **评测能力**           | ★★★★                           | 能建自己的 eval suite；会用轨迹级评分而不是只看最终答案                         |
| 6 | **RL / 后训练基础**    | ★★★（A 线）/ ★★★★★（B 线） | 懂 rollout、奖励设计、off-policy 偏差、TITO 这类关键取舍                        |

一句话：**这个岗位的护城河不是"会调 API"，而是"知道系统在长任务里会怎么坏、并提前堵住"。**

## 2. 20 周计划总览

按**业余 15 小时/周**设计；全职投入可压缩到 8–10 周（比例不变）。

| 阶段 | 周次   | 主题                                | 里程碑产出（作品集）                 |
| ---- | ------ | ----------------------------------- | ------------------------------------ |
| 一   | 1–4   | 打地基 + 手写最小 Agent Loop        | `mini-agent` 仓库 v0.1             |
| 二   | 5–8   | 上下文工程 + 工具层设计             | 对照实验博客 + v0.2                  |
| 三   | 9–12  | 生产化：权限 / 沙箱 / 可观测 / 编排 | 可交付的 Harness v1.0 + 架构对比长文 |
| 四   | 13–20 | 分线专精（A 平台 或 B RL）          | 深度项目（旗舰作品）                 |
| 五   | 持续   | 评测体系 + 开源 + 面试              | 自建 eval suite + 面试题库           |

**贯穿全程的三条铁律**

1. **每学一个概念，必须落到"我能在自己的代码里改哪一行"。**
2. **每周至少读 1 段真实源码**（先 Codex / Claude Code / OpenClaw / OpenHarness）。
3. **所有结论要有数据**。没有 A/B 对比的"我觉得更好"在面试里一文不值。

## 阶段一（第 1–4 周）打地基：把 Agent Loop 亲手写出来

### 目标

能准确回答："一次工具调用从用户按回车到看到结果，中间经过了哪些状态？"

### 学什么

- LLM 与推理接口：token、上下文窗口、`chat template`、采样参数（temperature/top_p）、流式返回。
- 工具调用机制：结构化输出的两种路线（原生 tool-call 通道 vs 文本+约束解码）。
- **MCP 协议规范**（读官方 spec：tools / resources / prompts 三类原语）。
- Agent Loop 的状态机：`think → tool_call → observation → think ...`；停止条件、步数预算、异常路径。

### 动手（关键）

写一个**不依赖任何 Agent 框架**的最小 agent（Python，200–400 行）：

- 接任意 OpenAI 兼容端点（DeepSeek / GLM / Kimi / OpenAI 都行）。
- 只实现 3 个工具：`read_file`、`write_file`、`run_shell`。
- 必须自己写：JSON 解析、解析失败重试、工具结果截断、最大步数保护。

**禁止使用 LangChain / AutoGen 之类的编排库。** 这个阶段你要理解的是机制，不是 API。

### 验收标准

- 给它一个带 bug 的小仓库，能自动定位并修复。
- 你能逐条解释它**失败的那几次**分别败在哪一步（是工具描述、上下文丢失、还是解析失败）。

### 产出

- GitHub：`mini-agent` v0.1，README 里写清**你做的每一个设计决策和理由**（这比代码本身更被面试官看重）。

## 阶段二（第 5–8 周）上下文工程与工具层

### 目标

能回答："上下文快满的时候你怎么办？为什么？"

### 学什么

- **上下文组装**：system prompt、工作区规则文件（AGENTS.md / CLAUDE.md）、工具描述、历史、检索结果各自的预算。
- **压缩策略**：摘要式、分层式、保留关键约束式；压缩的信息损失如何度量。
- **工具设计**：命名、描述措辞、参数粒度、幂等性、返回结果裁剪、**错误信息如何写成"可自纠的提示"**。
- **记忆**：会话内 vs 跨会话；明文记忆文件 vs 向量库的取舍。

### 动手

给 mini-agent 加四个能力：

1. 自动压缩（自己做，别调库）
2. 工具结果截断策略（头尾保留 vs 中间摘要）
3. 三级权限（只读 / 工作区可写 / 完全访问）
4. token 与成本计量

### 必做实验（这是你和其他候选人拉开差距的地方）

设计一组 A/B 对照，回答其中一个问题：

- 同一模型、同一任务集，把工具从 `grep` 改名为 `rg`，成功率变不变？
- 工具描述写 20 字 vs 写 200 字带示例，成功率与 token 成本如何权衡？
- 压缩阈值提前 10%，任务成功率掉多少？

跑 **≥200 次**，记录数据。（业界确有"工具命名显著影响表现"的现象——OpenAI 讲 Codex 时提到模型因为训练习惯对 `rg` 反应更好。你能自己复现或证伪它，就是硬通货。）

### 验收标准

- Agent 能连续完成 20 步以上的任务而不丢失原始目标。
- 你能画出自己 Harness 的**上下文预算表**（每一类内容占多少 token）。

### 产出

- 技术博客：《工具描述如何影响 Agent 成功率：一次 N 次运行的对照实验》，附原始数据。
- `mini-agent` v0.2。

## 阶段三（第 9–12 周）生产化：权限、沙箱、可观测、编排

### 目标

从"能跑的 demo"变成"别人敢用的工具"。

### 学什么

- **沙箱**：Linux 上的 Bubblewrap + seccomp / Landlock，macOS 的 Seatbelt，容器隔离的边界与代价。
- **权限模型**：allow / prompt / forbidden 策略引擎的设计（Codex 用 Starlark 写 execpolicy 是个很好的参考）。
- **可观测性**：结构化日志、OpenTelemetry、执行轨迹与回放。
- **多 Agent 编排**：任务板、依赖排序、**写入域划分**（避免两个 agent 改同一个文件）、worktree 隔离。
- **可靠性**：重试、幂等、检查点恢复、崩溃后继续。

### 阅读源码（本阶段重点）

对照读三个生产级 Harness，做一张对比表：运行时、工具层、记忆、权限、沙箱、多 Agent、可观测性。

- **Codex**（Rust，性能型）：[https://github.com/openai/codex](https://github.com/openai/codex)
- **Claude Code**（任务型，终端交互）：[https://github.com/anthropics/claude-code](https://github.com/anthropics/claude-code)
- **OpenClaw**（自驱型，后台常驻）：[https://github.com/openclaw/openclaw](https://github.com/openclaw/openclaw)
- 补充一个**可读性最好的 Python 开源 Harness**，适合入门读代码和提 PR：[https://github.com/HKUDS/OpenHarness](https://github.com/HKUDS/OpenHarness)

### 动手

给 mini-agent 加：

1. 子 Agent + 任务板 + 依赖排序（含写入域声明）
2. 完整轨迹日志与回放
3. 一个平台原生沙箱（先做 Linux，用 bubblewrap）
4. 危险命令拦截策略

### 验收标准

- 陌生人按你的 README 能在 10 分钟内跑起来。
- 你手动 kill 掉进程后，任务能恢复而不是从头再来。

### 产出

- `mini-agent` v1.0（可作为旗舰作品）。
- 长文：《三种 Harness 架构的取舍：Codex / Claude Code / OpenClaw 源码级对比》。

## 阶段四（第 13–20 周）分线专精

### 路线 A：平台 / 基础设施方向

- **内核化设计**：插件内核（"一切皆插件"）、能力注册与依赖注入、特性门控。
- **性能**：流式处理、并发工具调用、请求缓存（前缀缓存对多轮 agent 收益巨大）、prefill 成本控制。
- **协议生态**：自己写一个 MCP server 并接入你的 Harness。
- **企业能力**：多租户、审计、配额、私有化部署。
- 产出：把 mini-agent 做成**可被别人二次开发的平台**（写插件开发文档 + 示例插件）。

### 路线 B：RL / 后训练方向

- **RL 基础**：PPO → GRPO 的动机；on-policy vs off-policy；重要性采样与信任域。
- **Rollout 基础设施**：异步生成/训练解耦、轨迹重建、**TITO（token-in-token-out）** 为什么比 text-in-text-out 更准。
- **关键论文（必读）**
  - *Polar: Agentic RL on Any Harness at Scale*（arXiv:2605.24220）—— 把 Harness 当黑盒做 RL，并量化了"换 Harness 收益差 20+ 分"。
  - *WEFT: Scaling Tool-Use Post-Training for General-Purpose Agents*（arXiv:2609.36887）—— 只 scale 环境不够，要 scale"环境+任务+Harness+评估器"整个系统。
  - GLM-5 技术报告（arXiv:2602.15763）—— 异步 RL 基础设施、可验证环境构建（万级 SWE 环境）、思考模式设计。
- **必做实验**：挑一个小模型（3B–8B 级），用 GRPO 在一个你能自己验证的任务上训一版，报告基线对比。
- 产出：`agent-rl-playground` 仓库 + 实验报告。

## 阶段五（持续）评测、开源、面试

### 自建 eval suite（强烈建议，含金量极高）

- 30–50 个真实任务，覆盖：单文件修改、跨文件重构、失败恢复、权限拒绝、长任务。
- 双重打分：结果打分（测试过没过）+ **轨迹打分**（是否自检、是否重复试错、是否偏离目标）。
- 每次改 Harness 跑一遍回归——**这才是"工程"，否则你只是在做 demo**。

### 开源贡献

从低门槛开始：文档修正 → 工具实现 → 评测用例 → 子模块。
目标：20 周内 3–5 个被合并的 PR（哪怕很小）。

### 面试准备

**题型分布（按重要性）**

1. 系统设计："设计一个能安全执行 Shell 的 Agent 运行时" / "设计多 Agent 的写入冲突方案"
2. 编码："实现一个带重试与截断的工具调用循环" / "实现一个权限策略匹配器"
3. **排障（最容易拉开差距）**：给你一段失败的执行轨迹，问"哪里错了、怎么改"。
4. 模型侧（B 线）："为什么用 TITO" / "如何为一个终端任务设计奖励" / "环境规模化了为什么分数不涨"
5. 项目深挖：你的实验数据、你的权衡、你推翻过的假设。

**一条黄金答法**：**永远从失败模式出发讲设计，而不是从架构图出发。**

> "我先把长任务会怎么坏列出来：上下文丢失、工具误用、权限越界、崩溃不可恢复。然后每一项对应一个机制……"

**准备 3 个故事**（STAR 格式，带数字）：

- 一个你定位过的复杂 bug（体现排障能力）
- 一个你做过的技术权衡（体现判断力）
- 一个你量化过的改进（体现数据驱动）

## 5. 常见弯路（照着避免，能省三个月）

1. **从 LangChain 教程入门** → 你会变成"API 调用员"，不会做工程。
2. **只看不写** → 这个领域的认知只能在调试里长出来。
3. **忽视系统功底** → 并发、进程管理、文件系统语义、沙箱，才是 Harness 工程的硬门槛；很多人卡在这里而不是卡在模型上。
4. **一上来就学 RL** → 先把 Harness 做扎实；没有环境工程能力，RL 无从下手。
5. **只做 demo，不做长任务** → 短任务人人能做，长任务（20+ 步、崩溃可恢复、上下文不丢）才是分水岭。
6. **没有评测** → 你的"优化"无法证明有效，面试时会被一句话问穿。
7. **以为要会训大模型** → A 线完全不需要；B 线才需要，且重点是环境与 rollout，不是炼丹。

## 7. 一句话总结

**这个岗位不缺"会用工具的人"，缺的是"知道工具在长任务里会怎么坏、并能提前把坏掉的路堵上的人"。**
所以你的学习计划不应该围绕"学完某个框架"，而应该围绕**持续产出可验证的工程作品 + 带数据的实验结论**。
